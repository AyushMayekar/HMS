The short answer to "mixed timelines": it's intentional, not a bug. Every appointments row actually layers together five different moments: (1) what was known at booking, (2) ambient department-day operational context shared by every appointment that day, (3) what's only known at check-in, (4) what's only known once the visit resolves, and (5) a next-day forecast label. That's exactly the Blueprint's "NULL is a legitimate lifecycle state" rule (§4.3) in action — a still-booked future appointment has layers 3–5 all NULL because those facts genuinely don't exist yet, and no_show/cancelled rows never get check-in/service/billing timestamps because no visit happened to generate them.

appointments's 64 columns, grouped exactly as your blueprint groups them
Why the timelines mix — the five-layer breakdown, and why next_day_bed_demand/next_day_patient_flow deliberately "look ahead" (they're forecasting labels, not leakage)
Entity relationships between all tables
The full production workflow — booking → background operational context → ~24h-out no-show scoring → check-in → waiting-time scoring → visit → resolution → label finalization → audit/MLOps trail — each step mapped to exactly which columns it populates, per your blueprint's canonical flows (§18) and ML rules (§11).

One thing worth double-checking against your actual current schema before you build the feature builders: the blueprint's §11.1 rule that reminder_sent must never be used as a no-show prediction feature (only as an intervention you take after scoring) — that's the one place a naive "throw all appointment columns at the model" approach would quietly leak.


# Meridian Care Seed Data — Context, Column Reference & Data Workflow

This document explains what the Meridian Care Multispecialty Hospital (MCMH) seed
dataset is, what every column in every table means, how the tables relate to
each other, and — the part you specifically flagged — **why the `appointments`
table appears to mix timelines**, and how that maps onto the real product
workflow described in the Project Blueprint.

---

## 1. What This Dataset Is

The seed dataset is a **synthetic, reproducible snapshot** of what the
Meridian Care database would look like after roughly 12–13 months of
operation. It was generated by `seed_generator.py` to give the application,
analytics, and the two ML models (no-show prediction, waiting-time
prediction) something realistic to be built and tested against before any
real patient uses the system.

Per the Blueprint (§4.4), these are **data-science fixtures**, not real
patients: seeded `profiles.user_id` values are *not* required to equal a
real `auth.users.id`. Only users who sign up through the real product get a
profile whose `user_id` is a genuine Supabase Auth UUID. The two populations
coexist in the same `profiles` table by design.

The centerpiece of the dataset is `appointments` — a deliberately
**denormalized fact table** (64 columns) that plays three roles at once:
it is the operational appointment record, the analytics source, and the ML
training table. That triple role is exactly why its columns don't all
belong to "one moment in time" — more on that in §4.

## 4. Why the Columns "Mix Timelines" — And Why That's Correct

What you noticed is real, but it isn't an inconsistency in the data — it's
the defining feature of a **denormalized fact table**, and it's explicitly
called out in the Blueprint (§4.3, "Lifecycle Rule for NULLs"):

> *"NULL is a legitimate lifecycle state, not a validation error... UI
> summaries, analytics, and ML feature builders must select only fields
> relevant to the current use case."*

Every row in `appointments` actually layers together **five different
moments in time**, and each column group belongs to exactly one of them:

| Timeline | When it's known | Column groups |
|---|---|---|
| **① At booking** | The instant the appointment is created | Identity, Doctor/appointment context, Schedule, Patient history, Capacity/slot fields, Reminder/payment-at-booking fields |
| **② Ambient, that calendar day** | Continuously true for the whole department on that date, independent of any one patient | Queue/operational-state group (`department_active_doctors`, `arrivals_last_24h`, `occupied_beds`, etc.) |
| **③ At check-in / during the visit** | Only exists once the patient physically arrives | `queue_length_at_checkin`, `patients_ahead_at_checkin`, `actual_checkin_time`, `actual_service_start`, `actual_service_end`, `actual_wait_minutes` |
| **④ After the visit closes out** | Only exists once the appointment resolves | `appointment_status`, `billing_delay_days`, `satisfaction_score`, and the four historical ML targets (`no_show_target`, `waiting_time_target`, `billing_delay_target`, `satisfaction_target`) |
| **⑤ One day later (forecast label)** | Deliberately looks past the appointment's own date | `next_day_bed_demand`, `next_day_patient_flow` |

**Why group ② exists on a per-appointment row at all:** in the live
product, this operational context is *not* something a patient enters —
it's a snapshot of "what the department looked like that day," reused
identically by every appointment scheduled in that department on that
date (that's why, if you compare rows, many appointments in the same
department/day share identical values for `arrivals_last_24h`,
`occupied_beds`, etc.). It's stored per-appointment here purely so the ML
feature builder and analytics layer have a **self-contained training
table** — one row, one full feature vector — instead of needing a live
join against a separate operational-metrics table every time. In
production (Blueprint §11.4, "Live Analytics Execution Model"), the
*current* value of this same context is instead queried live from the
database on demand; it's only "frozen" onto a row here because this is a
training snapshot, not the live system.

**Why group ④/⑤ are `NULL` for future appointments:** any appointment
whose `scheduled_start` hadn't happened yet as of the seed's reference
"now" is left with `appointment_status = 'booked'` and every outcome/target
field `NULL`, because those outcomes genuinely aren't knowable yet. This is
intentional, and it's the same rule the real product must follow at
inference time — the Blueprint is explicit that the no-show model must
**never** use post-outcome fields (check-in time, service time, feedback)
as inputs, precisely because a real "not yet happened" appointment would
have `NULL` there too. If the seed data didn't null these out for future
appointments, it would silently teach a leakage pattern into anyone who
trained on it.

**Why `no_show`/`cancelled` rows don't get check-in/service timestamps:** a
patient who never showed up or who cancelled beforehand never generated a
check-in or service event — so those fields stay `NULL` rather than being
filled with a zero or a placeholder, again per the Lifecycle Rule for
NULLs.

**Why `next_day_bed_demand`/`next_day_patient_flow` look like they "peek
into the future":** they're not describing this appointment's own outcome
— they're **forecasting labels**. They record what the department's
occupancy/arrivals actually were on the *following* calendar day, so a
next-day forecasting model can be trained on "given everything known about
department conditions on day N, predict day N+1's bed demand / patient
flow." That's a different prediction task from the appointment-level
no-show/waiting-time models, and it's explicitly scoped as
analytics/forecasting rather than one of the two productized ML models
(Blueprint §11.3/§11.5).

So the "mixed timelines" you're seeing are five legitimate layers, not
corruption — the only two hard rules that must hold (and that the
validation report checks) are: (a) nothing in layers ③/④ is ever
populated for a row still in layer ① (i.e., a still-`booked`, future
appointment), and (b) a model predicting an outcome must only ever be
handed layer-①/② features that existed *before* the layer it's trying to
predict.

## 5. Entity Relationships

```text
departments ──1─┬─* doctors ──1─┬─* doctor_availability
                │               │
                │               └─* appointments ─┬─* payments
                │                                  ├─* reminders
                └──────────────* appointments      ├─* feedback
                                     │              └─* admin_requests
profiles (role=patient) ──1─*──────┘
profiles (role=staff/admin) ──── audit_logs.user_id
profiles (role=staff/admin) ──── admin_requests.assigned_to
profiles (role=staff/admin) ──── reminders.sent_by

appointments ──── admin_requests.appointment_id (optional)
payments     ──── admin_requests.payment_id     (optional)

dataset_versions ──1─*── model_versions ──1─*── prediction_logs
```

`appointments` is the hub: `payments`, `reminders`, `feedback`, and
`admin_requests` all hang off it, and `admin_requests` can *also*
optionally reference a `payments` row directly (e.g. a refund request tied
to a specific payment rather than the whole appointment).

## 6. The Real Product Workflow That *Would* Generate This Data

This is how the same columns get populated over time in the live system,
following the Blueprint's canonical flows (§18) and ML/analytics rules
(§11). Reading this alongside §4 should make clear which workflow step
"owns" which column group.

### Step 1 — Booking (patient-initiated, form or AI assistant)
`POST /appointments` (Blueprint §6.1, §18.1/§18.2). The backend resolves
the authenticated patient identity from the JWT, validates department/
doctor/slot, and writes a new `appointments` row with:
- **Identity** + **Doctor/appointment context** + **Schedule** fields,
- **Patient history** fields computed at that instant from the patient's
  prior appointments (never from anything after this booking),
- **Capacity/slot** fields from current `doctor_availability` state,
- `payment_required` / `payment_status_at_booking` / `invoice_amount` /
  `insurance_used` / `claim_required` if the appointment type requires
  payment,
- `reminder_sent = false` initially (a reminder hasn't gone out yet).

`appointment_status = 'booked'`. Everything in layers ③/④/⑤ is `NULL`.
An audit event is emitted (`audit_logs`).

### Step 2 — Ambient operational context (background, continuous)
Independent of any single booking, staff/admin dashboards continuously
reflect the department's current arrivals, admissions/discharges,
occupancy, and rolling averages (Blueprint §11.3/§11.4 — "Live Analytics
Execution Model"). In production this is computed **on demand from current
DB data**, not stored per appointment. It only gets "frozen" onto an
appointment row at training-snapshot time (which is exactly what the seed
generator did) or, potentially, at whatever lifecycle point the feature
builder actually needs it for inference.

### Step 3 — No-show prediction (~24h before the visit)
Blueprint §11.1 / §18.4. A scheduled job selects eligible upcoming
appointments, rebuilds the same **pre-outcome** feature set used in
training (patient history + booking context; **never**
`reminder_sent`, and **never** post-outcome fields), scores them with a
versioned model, and writes a `prediction_logs` row referencing that
`model_versions` entry. Staff sees a risk queue and can trigger a
reminder — which is what actually sets `reminder_sent = true` /
`reminder_hours_before` on the appointment and creates the corresponding
`reminders` row (with `sent_by` = the staff/admin who acted, or a system
identity for automated sends).

### Step 4 — Check-in (day of the visit)
Reception marks the patient as arrived. This is the first moment layer
③ becomes real: `actual_checkin_time` is set, and
`queue_length_at_checkin` / `patients_ahead_at_checkin` are read from the
department's live queue state. This is also the trigger point for
**waiting-time prediction** (Blueprint §11.2/§18.5) — run here, not at
booking, because its required features (queue length, patients ahead,
recent service time) don't exist until check-in. That inference also logs
to `prediction_logs`.

### Step 5 — Visit happens
Staff/system records `actual_service_start` and `actual_service_end` as
the consultation proceeds. `actual_wait_minutes` is derivable as
`actual_service_start − actual_checkin_time`.

### Step 6 — Resolution
Once the visit concludes (or the slot passes without a check-in, or the
patient cancels beforehand), `appointment_status` is finalized to
`completed` / `no_show` / `cancelled`:
- If `completed`: `actual_*` timestamps are set, and if payment was
  required, the payment flow (Blueprint §7.1) runs, eventually producing
  a `payments` row and a `billing_delay_days` value once payment
  finalizes.
- If the patient later submits feedback, a `feedback` row is created and
  `satisfaction_score` is copied back onto the appointment.
- `no_show`/`cancelled` appointments never populate the check-in/service/
  billing/satisfaction fields — there was no visit to generate them.

### Step 7 — Historical labels finalize
Once the appointment's fate is fully known, `no_show_target`,
`waiting_time_target`, `billing_delay_target`, and `satisfaction_target`
become valid **historical labels** — this is exactly what the next
training run's `dataset_versions` snapshot would pull from. Separately,
once the *following* calendar day's actual department numbers are known,
they get attached backward as that day's `next_day_bed_demand` /
`next_day_patient_flow` forecast labels.

### Step 8 — Governance and traceability (continuous)
Every privileged mutation along the way (reminder sent, request resolved,
KB published, refund processed) produces an `audit_logs` row. Every model
training run gets a `dataset_versions` entry; every deployed model gets a
`model_versions` entry; every inference (Step 3 and Step 4) gets a
`prediction_logs` entry referencing that model version — so any prediction
can always be traced back to exactly which model produced it and what it
saw.

---

## 7. One-Line Summary

`appointments` isn't a transaction log of one event — it's a **rolling
snapshot table** that accumulates five layers of fact over an
appointment's real lifecycle (booked → ambient context → checked-in →
resolved → labeled), and the seed generator populates each layer only when
that layer would genuinely exist yet. The "mixed timelines" are the model
working correctly, not a defect to fix.
